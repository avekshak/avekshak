Contributor Guide

Build on Avekshak

Everything you need to run the stack locally, understand the architecture, add a new data connector, write detection rules, and get a PR merged. No prior security background required — just TypeScript and curiosity.

Node.js 22 TypeScript pnpm workspaces Docker Compose BullMQ · Redis PostgreSQL · Drizzle
01 — Dev Setup

Get the full stack running

The entire platform — Postgres, Redis, all services — runs locally via Docker Compose and pnpm. You need Docker Desktop, Node.js 22+, and pnpm 9+. For offline AI inference use Ollama; for cloud inference use an Anthropic API key.

01

Clone and install

Fork the repo, then clone your fork and install all workspace dependencies in one command.

02

Start the infrastructure

Brings up Postgres 16 and Redis 7 in Docker. Runs in the background.

03

Configure environment

Copy .env.example to .env. Set ANTHROPIC_API_KEY for Claude, or set LLM_PROVIDER=ollama to run entirely offline.

04

Build and migrate

Compiles all TypeScript packages and runs the Drizzle migrations to set up the Postgres schema.

05

Seed and smoke-test

Replays the demo attack night through the real pipeline. All 11 assertions should pass.

# 1 — clone + install
git clone https://github.com/YOUR_USERNAME/avekshak.git && cd avekshak
pnpm install

# 2 — start Postgres + Redis
docker compose up -d

# 3 — configure env
cp .env.example .env
# edit .env — set ANTHROPIC_API_KEY or LLM_PROVIDER=ollama

# 4 — build all packages + run DB migrations
pnpm -r build
pnpm --filter @avekshak/db run migrate

# 5 — seed the demo night and verify everything passes
make seed
make smoke    # exits 0 when all 11 assertions pass
💡
Ollama offline mode: Run ollama pull llama3.2:3b then set LLM_PROVIDER=ollama in .env. The agent uses the Ollama HTTP API at localhost:11434 — no API key, no data egress.

Individual service dev mode

Each service compiles independently. Run the one you're working on in watch mode:

# watch-compile a single service
pnpm --filter @avekshak/ingest    dev
pnpm --filter @avekshak/fusion    dev
pnpm --filter @avekshak/correlation dev
pnpm --filter @avekshak/agent     dev
pnpm --filter @avekshak/api       dev

# run all tests (all packages, all services)
pnpm -r test
02 — Architecture

How the codebase is structured

Avekshak is a pnpm monorepo. Five pipeline services communicate through Redis queues. Three shared packages own every cross-cutting concern — schema, database, and queuing. No service imports from another service directly. 

services/
  ingest/         # Connectors: syslog, wazuh, aws — produces NormalizedEvent
    src/connectors/  # One subdir per source (aws/, syslog/, wazuh/)
    src/normalize/   # Pure transform functions (no I/O)
    src/pipeline/   # Queue writer + BullMQ worker factory
    fixtures/        # Sample JSON payloads for testing
    scripts/         # Integration gate scripts
  fusion/          # Detection engine — evaluates every event against YAML rules
    src/rules/       # loader.ts + evaluator.ts
    src/pipeline/   # promote.ts (single-event) + windowCounter.ts (temporal)
  correlation/     # Groups alerts into incidents by shared actor IP/user/host
    src/correlate/  # correlator.ts, keys.ts, lifecycle.ts
  agent/           # 3-tier AI triage: scorer → LLM → groundedness gate
    src/score/       # scoreTriage.ts, keywords.ts, groundedness.ts
    src/llm/         # claude.ts + ollama.ts + provider.ts (strategy pattern)
    src/triage/      # runner.ts orchestrates the 3 tiers
  api/             # Fastify REST: GET /incidents, POST approve/reject

packages/
  schema/          # NormalizedEvent type + Zod schema — the universal event shape
  db/              # Drizzle schema, migrations, getDb(), appendLedger()
  queue/           # TypedQueue — createQueue() + createWorker() wrappers

detections/rules.yaml  # All detection rules live here — no code change needed
docker-compose.yml     # Postgres 16 + Redis 7
Makefile               # up / bootstrap / seed / smoke shortcuts

Data flow — one event's journey

📡

1 · Ingest

Connector receives raw event (syslog line, Wazuh doc, AWS record). Normalizer converts it to NormalizedEvent. Enqueued to INGEST_QUEUE.

→ Redis: "events"
🔍

2 · Fusion

Dequeues NormalizedEvent. Evaluates all YAML rules. Matching rules produce Alert rows, written to Postgres. Windowed rules use Redis counters.

→ Redis: "alerts"
🔗

3 · Correlation

Groups alerts sharing the same actor.ip, actor.user, or target.host into one Incident row. Writes to incidents and incident_alerts tables.

→ Postgres: "incidents"
🤖

4 · Agent

Deterministic score → LLM verdict → groundedness check. Every step appended to the ledger. Incident status set to triaged.

→ Postgres: "ledger"
✋

5 · API + Human

Analyst reads incident via GET /incidents/:id. Calls POST /incidents/:id/approve or /reject. Single guarded UPDATE prevents double-decide.

→ Postgres: "approvals"

Shared packages — the contracts

@avekshak/schema

NormalizedEvent TypeScript type + Zod validator. All connectors produce it; fusion, correlation, and agent consume it. One source of truth.

@avekshak/db

Drizzle ORM schema for every table, getDb() connection factory, and appendLedger(). No service defines its own tables.

@avekshak/queue

createQueue<T>(name) and createWorker<T>(name, handler). Thin typed wrapper over BullMQ so each service only sees the right message shape.

03 — Adding a Connector

The 3-file connector pattern

Every connector lives in its own subdirectory under services/ingest/src/connectors/. The pattern is always three files: a pure processor, an entrypoint, and co-located tests. The processor has no I/O — it only transforms and enqueues, which makes it trivially testable.

reader.ts / listener.ts / poller.ts
The pure processor. Receives raw data, calls the normalizer, enqueues each event. No startup logic. Returns a typed result. This is what your tests call directly.
index.ts
Startup entrypoint. Opens the connection (UDP socket, HTTP poll, file read). Calls the processor in a loop. Handles reconnect. Not tested — keep it thin.
reader.test.ts
Co-located unit tests for the processor only. Use fixture JSON from services/ingest/fixtures/. Tests run with pnpm --filter @avekshak/ingest test.
📌
UUIDv5 for deduplication: If your source has a stable event identifier (AWS eventID, Wazuh _id, etc.), derive the NormalizedEvent.id with uuidv5(stableKey, YOUR_NAMESPACE_UUID) instead of uuidv4(). This makes re-ingest idempotent — the DB write uses onConflictDoNothing on the PK.

Skeleton: a new connector

// services/ingest/src/connectors/mysource/processor.ts
import { v5 as uuidv5 } from "uuid";
import { normalizeMySource } from "../../normalize/mysource.js";
import { type TypedQueue } from "@avekshak/queue";
import { type NormalizedEvent } from "@avekshak/schema";

// Stable namespace UUID — generate once, never change
const MY_NS = "xxxxxxxx-xxxx-5xxx-yxxx-xxxxxxxxxxxx";

export async function processRecords(
  records: unknown[],
  queue:   TypedQueue<NormalizedEvent>,
): Promise<{ enqueued: number; skipped: number }> {
  let enqueued = 0, skipped = 0;

  for (const raw of records) {
    const stableId = uuidv5(String((raw as any).id), MY_NS);
    const ev = normalizeMySource(raw, stableId);
    if (!ev) { skipped++; continue; }
    await queue.enqueue("event", ev);
    enqueued++;
  }

  return { enqueued, skipped };
}
// services/ingest/src/connectors/mysource/index.ts
import { createQueue } from "@avekshak/queue";
import { type NormalizedEvent } from "@avekshak/schema";
import { INGEST_QUEUE } from "../../pipeline/ingestQueue.js";
import { processRecords } from "./processor.js";

const POLL_MS = 30_000;

export async function startMySourceConnector(): Promise<void> {
  const queue = createQueue<NormalizedEvent>(INGEST_QUEUE);
  let cursor: string | undefined;

  while (true) {
    const { records, nextCursor } = await fetchFromApi(cursor);
    const { enqueued } = await processRecords(records, queue);
    console.log(`[mysource] enqueued=${enqueued}`);
    cursor = nextCursor;
    await new Promise(r => setTimeout(r, POLL_MS));
  }
}
// services/ingest/src/connectors/mysource/processor.test.ts
import { describe, it, expect, vi } from "vitest";
import { processRecords } from "./processor.js";
import sample from "../../../fixtures/mysource.json";

describe("processRecords", () => {
  const makeQueue = () => ({ enqueue: vi.fn().mockResolvedValue(undefined) });

  it("enqueues a valid record", async () => {
    const q = makeQueue();
    const { enqueued, skipped } = await processRecords([sample[0]], q as any);
    expect(enqueued).toBe(1);
    expect(skipped).toBe(0);
    expect(q.enqueue).toHaveBeenCalledOnce();
  });

  it("produces deterministic IDs (dedupe)", async () => {
    const q1 = makeQueue(), q2 = makeQueue();
    await processRecords([sample[0]], q1 as any);
    await processRecords([sample[0]], q2 as any);
    const id1 = q1.enqueue.mock.calls[0][1].id;
    const id2 = q2.enqueue.mock.calls[0][1].id;
    expect(id1).toBe(id2); // same input → same ID always
  });
});

Also add a normalizer

The normalizer lives in services/ingest/src/normalize/mysource.ts and is a pure function — no imports from queue or db, just transforms unknown → NormalizedEvent | null. Use NormalizedEventSchema.safeParse() as the last step so invalid shapes are rejected cleanly.

✅
Checklist before opening a connector PR: normalizer in src/normalize/ · processor in src/connectors/mysource/processor.ts · entrypoint in src/connectors/mysource/index.ts · co-located tests · fixture JSON in fixtures/ · deterministic ID with uuidv5 if source has stable IDs · pnpm --filter @avekshak/ingest test passing.
04 — Detection Rules

Write rules without touching TypeScript

All detection rules live in detections/rules.yaml. The rule loader validates on startup — a typo gives you a clear error, not a silent skip. No code change required to add a new rule.

Rule anatomy

detections/rules.yaml YAML 
# Minimal rule — fires when ALL conditions match
- id: your-rule-id              # unique, kebab-case
  title: "Human-readable title"  # shown in the dashboard
  severity: 70                    # 0–100, used by scorer
  when:
    - { field: category, op: eq,       value: "authentication" }
    - { field: outcome,  op: eq,       value: "failure" }
    - { field: actor.ip, op: exists,   value: true }

# Windowed rule — fires after N events matching conditions within T seconds
- id: brute-force-logins
  title: "Brute-force authentication"
  severity: 70
  when:
    - { field: category, op: eq, value: "authentication" }
    - { field: outcome,  op: eq, value: "failure" }
    - { field: actor.ip, op: exists, value: true }
  window:
    groupBy:   actor.ip   # Redis key suffix
    threshold: 5           # fire when count reaches this
    seconds:   300         # sliding window size

⚠️
Rule IDs must be unique. The rule loader throws on startup if two rules share an ID. Use kebab-case. If you're adding a rule for a specific attack pattern, prefix it with the source: aws-, syslog-, wazuh-.
05 — Running Tests

Test structure and commands

Tests are co-located next to the files they test — foo.ts and foo.test.ts sit in the same directory. We use Vitest. There are no separate tests/ folders; if you see one, it's legacy and being removed. 

# run all tests across all packages and services
pnpm -r test

# run tests for one service only
pnpm --filter @avekshak/ingest     test

# run tests in watch mode while developing
pnpm --filter @avekshak/ingest test -- --watch

# integration check: run the full pipeline end-to-end (requires running infra)

06 — Branch Workflow

How changes get merged

Avekshak uses a two-stage promotion model. Your PR targets test, not main. Once CI passes on test, it auto-promotes to main. Never open a PR directly against main.

dev-yourname
your feature branch
→
PR + review + CI
test
integration branch
→
CI passes → auto-promote
main
protected, always green
01

Branch off test

Name your branch dev-<yourname> or feat/<feature-name>. Branch from the latest test, not main.

02

Open PR targeting test

Write a clear description. CI runs CodeQL (security), type-check, and pnpm -r test automatically. Labels are auto-applied from your changed files.

03

Commit message format

Use conventional commits: feat(ingest): add splunk connector · fix(agent): handle empty LLM response · test(fusion): add windowed rule coverage. Types: feat fix docs test refactor chore.

04

Merge to test

Once a reviewer approves and CI is green, merge. CI runs again on test after merge.

05

Auto-promotion to main

If the CI run on test passes, .github/workflows/promote-test-to-main.yml opens a fast-forward PR to main automatically. You don't touch main.

⚠️
Never PR directly to main. main is protected. Only the auto-promotion workflow can push to it. If your branch is out of date, merge origin/test into your branch — don't rebase onto main.
07 — Code Reference

Key interfaces and APIs

The types and functions every contributor touches most often.

// packages/schema/src/index.ts
export interface NormalizedEvent {
  id:       string;        // uuid (v4 or v5 for deduplication)
  ts:       string;        // ISO 8601 event timestamp
  source:   "syslog" | "wazuh" | "aws";
  category: string;        // "authentication" | "cloud" | "syscheck" | "system"
  action:   string;        // "login_failed" | "Exfiltration:S3/…" | …
  outcome:  "success" | "failure" | "unknown";
  severity: number;        // 0–100
  actor: {
    user?: string;         // "root", "svc-backup"
    ip?:   string;         // "203.0.113.50"
  };
  target: {
    host?:     string;     // "db-prod-1"
    resource?: string;     // "s3://corp-financials-prod"
    ip?:       string;
  };
  location?: {
    country?: string;      // ISO 3166-1 alpha-2, e.g. "RU"
    city?:    string;
  };
  raw: object;             // original vendor payload, untouched
}

// Always validate before returning from a normalizer:
const parsed = NormalizedEventSchema.safeParse(candidate);
return parsed.success ? parsed.data : null;
// packages/queue/src/index.ts

// Create a strongly-typed queue handle
const q = createQueue<NormalizedEvent>("events");
await q.enqueue("event", normalizedEvent);

// Create a worker that consumes from the queue
const worker = createWorker<NormalizedEvent>(
  "events",
  async (job) => {
    await processEvent(job.data);  // job.data is typed NormalizedEvent
  }
);

// Named queues used in the pipeline:
// INGEST_QUEUE  = "events"   (ingest → fusion)
// DETECT_QUEUE  = "alerts"   (fusion → correlation)
// TRIAGE_QUEUE  = "triage"   (correlation → agent)
// packages/db/src/ledger.ts

// Every step the agent or system takes is appended here — never updated or deleted
await appendLedger(
  incidentId,              // UUID of the incident
  "agent",               // actor: "agent" | "system" | "human"
  "triage.score",        // action string (dot-namespaced)
  {                        // detail: any JSON-serializable object
    confidence: 0.95,
    verdict:    "critical",
    basis: ["high severity (0.51)", "'exfiltration' keyword (+0.35)"],
  }
);

// Ledger entries in the pipeline:
// triage.context_gathered — context loaded for scoring
// triage.score            — deterministic score result
// triage.verdict          — final LLM verdict
// triage.fallback         — LLM failed, using deterministic score
// triage.gate_demotion    — groundedness check demoted verdict
// incident.status_changed — status transition
// human.decision          — analyst approved or rejected
// response.executed       — response action taken (or dry-run)
// services/api/src/incidents.ts

// Concurrency-safe approval gate: single UPDATE WHERE status='triaged'
// Returns 409 if incident was already decided or doesn't exist
export async function decideIncident(
  id:       string,
  decision: "approve" | "reject",
): Promise<DecisionResult> {

  const rows = await db
    .update(incidents)
    .set({ status: decision === "approve" ? "approved" : "rejected" })
    .where(and(
      eq(incidents.id, id),
      eq(incidents.status, "triaged"), // only acts on triaged
    ))
    .returning();

  if (rows.length === 0) throw new InvalidDecisionStateError(id);
  await appendLedger(id, "human", "human.decision", { decision });

  // asymmetry: approve triggers response, reject triggers nothing
  const response = decision === "approve"
    ? await planResponse(rows[0])
    : null;

  return { incidentId: id, status: rows[0].status, response };
}
08 — FAQ

Common contributor questions

How do I add support for a new log source? ▼
Three files: src/connectors/mysource/processor.ts (pure transform + enqueue), src/connectors/mysource/index.ts (startup + I/O), and src/connectors/mysource/processor.test.ts (unit tests with mocked queue). Also add a normalizer at src/normalize/mysource.ts and fixture JSON at fixtures/mysource.json. See the Connectors section above for a full skeleton.
How do I change the Postgres schema? ▼
Edit packages/db/src/schema.ts. Then run pnpm --filter @avekshak/db exec drizzle-kit generate to generate a new migration file, and pnpm --filter @avekshak/db run migrate to apply it. Never edit migration files by hand — always generate them from the schema.
What's the difference between make seed and make smoke? ▼
make seed runs the full demo attack night through the real pipeline and prints a human-readable summary of which incidents formed. Use it to populate the dashboard for demos or manual exploration.

make smoke runs the same pipeline but asserts 11 specific properties — exfil is critical, root login stays suspicious, brute force and exfil are separate incidents, ledger entries are ordered, etc. It exits non-zero if any assertion fails. Use it in CI or to verify after a code change.
How does the AI provider switching work? ▼
The agent uses a strategy pattern in services/agent/src/llm/provider.ts. Set LLM_PROVIDER=claude in .env to use the Anthropic Claude API (requires ANTHROPIC_API_KEY). Set LLM_PROVIDER=ollama to use a local Ollama model (default llama3.2:3b, configurable via OLLAMA_MODEL). Both providers implement the same interface, so the triage runner doesn't know which one it's using.
Where do I put integration tests vs unit tests? ▼
Unit tests go co-located next to the file they test: foo.ts → foo.test.ts. They run with pnpm test, use mocks, and should need no running infrastructure.

Integration scripts go in services/<name>/scripts/check-*.ts. They require a live Postgres + Redis, run sequentially, and are invoked via make smoke. Don't add them to pnpm test — they're too slow and stateful for a unit test runner.
How does deduplication work across re-ingest? ▼
If a connector re-ingests the same raw event (e.g., a Wazuh re-poll returns events already seen), the event ID must be the same both times. Use uuidv5(stableKey, CONNECTOR_NAMESPACE) where stableKey is the vendor's own unique identifier (AWS eventID, Wazuh _id). The DB write uses .onConflictDoNothing({ target: events.id }), so the second insert is silently ignored and the event is not double-counted.
Can I add a detection rule without opening a PR? ▼
Yes — if you're running your own fork, just edit detections/rules.yaml and restart the fusion service. No compilation needed. The loader validates on startup, so a YAML error gives you a descriptive message immediately. If you want to contribute the rule upstream, open a PR following the standard workflow (branch from test, PR to test).
How do I debug a failing make smoke assertion? ▼
Run the individual phase scripts to narrow it down: pnpm --filter @avekshak/ingest exec ts-node scripts/check-phase1-integration.ts for ingest, check-phase2 for fusion, etc. Each script prints what it found and what it expected. The most common cause is a stale database — run make seed (not just make smoke) to repopulate, then re-run smoke.
