The Problem

The alert that matters is already buried.

Every company that runs security tools — firewalls, cloud accounts, login systems — generates alerts when something looks wrong. A mid-sized business produces thousands of these every single day. Each one arrives as its own separate line on a screen, demanding a human decision: is this an attack, or is this nothing?

No person can read five thousand alerts a day. So they stop reading. And the moment they stop reading, the alerts stop protecting anyone.

What actually happens

At 2:00 a.m., a security system fires alert number 4,312: a server in another country is quietly copying the company's customer database. It looks identical to the 4,311 alerts before it. The night-shift automation had already silenced the whole category an hour earlier because it was "too noisy." Nobody saw it until the data was gone.

severity: critical · status: auto-muted · time-to-human: never

The problem is not that the alert was wrong. The alert was perfectly correct. The problem is that it looked exactly like thousands of harmless ones, and there was no human attention left to spend on it.

▲ Volume destroys signal

When everything is flagged, nothing is flagged. A critical alert and a routine one occupy the same single line on the same crowded screen.

▲ No context per alert

Each alert is isolated. A human must manually gather the logs, the location, the user, and the history before they can even judge it.

▲ Fatigue leads to muting

Overwhelmed teams silence whole categories to survive the shift. The silence is where real attacks live.

▲ Expensive to solve the old way

Enterprise platforms that help cost hundreds of thousands a year and still send the data to someone else's cloud.

The Solution

Sentinel reads them so a human never has to read five thousand.

Instead of showing a person thousands of disconnected alerts, Sentinel does the first pass of the work automatically. It collects the alerts, recognizes which ones belong to the same event, bundles them into a single incident, and hands an AI investigator the whole picture at once.

1

It groups related alerts into one incident

Forty alerts from the same attacker hitting the same server across ten minutes become a single incident — not forty separate decisions.

2

An AI agent investigates each incident

The agent pulls the relevant logs, checks the location, the user, and the pattern, then writes a plain-language verdict: is this an attack, how confident it is, and what it recommends.

3

Every step is written into a ledger

Each query the agent ran and each piece of evidence it used is recorded. The decision is never a black box — a human can read exactly how the conclusion was reached.

4

Nothing acts without human approval

The AI proposes. The human decides. No account is locked and no server is touched until a person clicks approve.

5

It runs entirely on your own machine

The AI model runs locally. No data leaves the building, and there are no per-query fees to an outside provider.

The same night, with Sentinel

The 40 alerts about the overseas server copying the database collapse into one incident titled "Possible data exfiltration — external host." The AI investigates, notes the destination is an unknown foreign IP pulling gigabytes at 2 a.m., marks it critical — 94% confidence, and recommends cutting the connection. A human sees one clear incident at the top of the list, reads the evidence, and approves the block in seconds.

incident: #2 · alerts grouped: 40 → 1 · verdict: critical · time-to-human: immediate
And it tells the harmless ones apart too

Another incident that night: a company owner logging into the admin account from a holiday location at 4 a.m. Alarming at first glance. The AI checks the history, sees it is the owner's own known account and device, marks it low risk, and files it quietly — without ever waking anyone up.

The MVP

What we build first, and what waits.

The goal is a working product in two weeks that proves the full loop end to end: real data in, grouped incidents out, an AI verdict on each, and a human approving the action. We deliberately keep the first version small and focused so the core value is provable before we expand.

▸ In the first version

  • Three data connectors: cloud logs, server logs, and generic system logs
  • A detection engine with a focused set of high-value rules
  • Grouping alerts into incidents — the central feature
  • A local AI agent that investigates and writes verdicts
  • The investigation ledger for full transparency
  • A human approval step before any action
  • A clean dashboard to view and act on incidents

▸ Deliberately left for later

  • Dozens of additional connectors
  • Large-scale data lake and graph storage
  • Automated response playbooks
  • Enterprise login, multi-factor, and multi-tenant support
  • Shared threat-intelligence network
  • Behavior analytics and deception tooling
Under The Hood

The technology for the technical reader

Sentinel is built on a modern, fully open-source stack. Everything runs locally through Docker, so a single command stands up the whole system on one machine.

The stack

LayerChoiceRole
BackendNode.js + TypeScript + FastifyAPI and pipeline services
DatabasePostgreSQLAlerts, incidents, rules, ledger
QueueBullMQ + RedisDecouples ingestion from detection
AI ModelOllama · llama3.2:3bLocal, private LLM triage — no API keys
FrontendReact + ViteIncident dashboard and approval UI
InfrastructureDocker ComposeOne-command local deployment

The only meaningful simplification from the full architecture is using a Redis-backed queue instead of a heavier event-streaming system. The producer/consumer boundary is kept clean, so this can be upgraded later without touching the core logic.

Folder structure

/services /ingest # Connector pollers (Cloud, Server, Syslog) /fusion # Detection engine + alert promotion /correlation # Groups alerts into incidents /agent # LLM triage + ledger writer /api # REST API /apps /web # React dashboard /packages /schema # Shared types (event, alert, incident) /queue # BullMQ wrapper /detections # YAML detection rules docker-compose.yml # Entire stack, one file
